# NVIDIA GPU Lowering Configuration Architecture in Nova

This document details the changes made to introduce a data-driven GPU lowering configuration in the Nova compiler. This architecture was modeled directly after the IREE compiler infrastructure, adapting its comprehensive configuration abstractions into a lightweight, self-contained mechanism tailored for Nova.

---

## 1. Dialect & Core Infrastructure
### `include/Compiler/Dialect/nova/NovaOps.td`
* **What we did**: Added the `Nova_LoweringConfigAttr` attribute definition and the `Nova_NVMMAIntrinsicKind` enum. The attribute acts as a container for lowering decisions (`workgroup`, `reduction`, `mma_kind`, `promoted_operands`).
* **Comparison with IREE**: Mirrors IREE's `IREEGPUAttrs.td` (specifically `IREEGPU_LoweringConfigAttr` and `IREEGPU_MMAAttr`). While IREE uses complex custom TableGen attribute structs with explicitly typed fields, Nova simplifies this by wrapping a standard `DictionaryAttr`. This avoids introducing entirely new MLIR dialects while achieving the exact same functional outcome.

## 2. Configuration Utilities
### `include/Compiler/Transforms/LLVMGPU/NovaGPULoweringConfigUtils.h`
### `lib/Transforms/LLVMGPU/NovaGPULoweringConfigUtils.cpp`
* **What we did**: Created utility functions (`getLoweringConfigTileSizes`, `getMmaKindRaw`, `appendPromotedOperandsList`) to standardize reading and writing to the new dictionary attribute.
* **Comparison with IREE**: Mirrors IREE's `iree/compiler/Codegen/Dialect/GPU/IR/GPULoweringConfigUtils.h`. IREE uses concrete C++ wrapper classes generated by TableGen for its attributes. Nova achieves the same API surface by using string keys (like `"mma_kind"`) on the `DictionaryAttr`. The resulting C++ developer experience inside passes is virtually identical.

## 3. Hardware Target Modeling
### `include/Compiler/Transforms/LLVMGPU/NVIDIATargetUtils.h`
### `lib/Transforms/LLVMGPU/NVIDIATargetUtils.cpp`
* **What we did**: Defined the `NVIDIATargetInfo` and `NVMMAIntrinsicInfo` structs, and implemented a lookup table spanning Volta (`sm_70`) to Hopper (`sm_90`). This table stores SM counts, shared memory constraints, and supported MMA instructions.
* **Comparison with IREE**: Directly mirrors IREE's `iree/compiler/Codegen/Dialect/GPU/TargetUtils/KnownTargets.cpp` (`getCUDATargetDetails()`). In IREE, this data is encapsulated into a complex `IREEGPU_TargetAttr` attached to the module. In Nova, we keep this as a lightweight C++ struct queried directly during the configuration pass, bypassing the overhead of serializing deep hardware specs into MLIR IR while keeping the backend logic identical.

## 4. Heuristic & Schedule Deduction
### `include/Compiler/Transforms/LLVMGPU/NovaKernelConfig.h`
### `lib/Transforms/LLVMGPU/NovaKernelConfig.cpp`
* **What we did**: Implemented `setMatmulLoweringConfig`, which calculates optimal workgroup and reduction tile sizes. It computes a 4-subgroup-per-workgroup schedule if NVIDIA MMA intrinsics are available on the target architecture, otherwise falling back to a hardcoded `kSimtTable`.
* **Comparison with IREE**: Mirrors IREE's `iree/compiler/Codegen/LLVMGPU/KernelConfig.cpp` (specifically functions like `setMatmulVectorDistributionConfig` and `deduceMMASchedule`). Nova adapts IREE's subgroup dimensioning logic directly but narrows the scope exclusively to NVIDIA architectures, stripping away abstractions required by IREE to simultaneously support Vulkan, Metal, and ROCm.

## 5. Pass Execution & Pipeline Integration
### `lib/Transforms/LLVMGPU/NovaGPUSelectLoweringStrategy.cpp`
* **What we did**: Added a standalone pass (`nova-gpu-select-lowering-strategy`) accepting a `--cuda-arch` flag. It maps the target, evaluates the heuristics, and stamps the lowering config onto every `linalg` contraction operation.
* **Comparison with IREE**: Mirrors IREE's `LLVMGPUSelectLoweringStrategy.cpp`. IREE utilizes dialect interfaces (`LoweringConfigInterface`) to abstract strategy application. Nova attaches the pass specifically to `linalg` operations inside the main pipeline wrapper.

### `lib/Transforms/LLVMGPU/Passes.h` & `Passes.cpp`
* **What we did**: Added the strategy pass as **Step 0** inside `addNovaGPUOptimizedPipeline`. This ensures the config attribute exists *before* any tiling or distribution runs.
* **Comparison with IREE**: Exactly parallels IREE's pipeline design principle: strictly separate the *decision-making* phase (strategy pass) from the *IR mutation* phase (tiling passes).

## 6. Config-Driven Tiling & Promotion
### `lib/Transforms/LLVMGPU/NovaGPUApplyTilingLevelReduction.cpp`
* **What we did**: Updated the `getTileSizes` logic for the K-Reduction loop to first attempt reading the tile size from the `lowering_config` attribute.
* **Comparison with IREE**: Mirrors IREE's `GPUApplyTilingLevel.cpp`, completely decoupling the transformation mechanism from magic numbers.

### `lib/Transforms/LLVMGPU/NovaGPUPromoteMatmulOperands.cpp`
* **What we did**: Modified the `runOnOperation` loop to query the `promoted_operands` list from the config attribute to decide which tensors go to shared memory.
* **Comparison with IREE**: Mirrors how IREE's `GPUPromoteMatmulOperands.cpp` dynamically handles promotion based on strategy logic (e.g. promoting only `A`, `A` and `B`, or `C` for accumulation) rather than indiscriminately operating on operand indices 0 and 1.

## 7. Verification Setup
### `test/pipeline-tests/11_lowering_config.mlir`
* **What we did**: Created an isolated FileCheck suite ensuring different outputs are generated depending on the `--nova-cuda-arch` flag (`sm_75` vs `sm_80`), and verifying the full tile-pad-promote pipeline successfully ingests the generated config.
* **Comparison with IREE**: Behaves precisely like IREE’s lowering strategy tests, verifying that the compiler frontend correctly passes configuration states down to the MLIR optimization layers.
